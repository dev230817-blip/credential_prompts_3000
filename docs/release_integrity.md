# release_integrity.md — 逐字节保真与 Git 属性

## 1. 为什么必须禁止换行转换

本仓库的 CSV 里同时存在两种换行：

- **记录分隔换行**：每行一条记录，行结束符是 CRLF；
- **单元格内部换行**：`prompt` 正文本身含换行，导出时按 CSV 引号规则包在引号内。

如果启用 Git 的换行转换（`text` 属性或 `eol=`），检出时会同时改写这两类换行。结果是：
磁盘上的文件与 ZIP 一致，但**入库后再检出的文件字节不同**。哈希清单因此失去意义。

## 2. 当前设置

`.gitattributes` 全文的核心只有一条：

```
* -text
```

`-text` 表示这些路径不做行尾转换、不做编码归一化，按原字节存储。随后只对真正的二进制格式
（PNG／JPEG／PDF／ZIP）使用 `binary` 宏，它等价于 `-diff -merge -text`，不会重新启用转换。

**文件中没有任何后续规则重新启用 `text` 或设置 `eol=`。** 新增文件时不要为已纳入哈希清单的
路径添加这两类属性；如果确实需要，必须先重新封存并重算清单。

## 3. 各类文件的现有字节形态

| 文件 | 编码 | 行结束符 |
| --- | --- | --- |
| `*.jsonl`、`*.json`、`*.md`、`*.py`、`prompts.txt` | UTF-8 无 BOM | LF |
| `*.csv` | UTF-8 无 BOM | CRLF（单元格内部换行按 CSV 引号规则保留） |
| `SHA256SUMS.txt` | UTF-8 无 BOM | LF |

## 4. 需要验证的三段一致

封存后的正确性要求下面三段逐字节相同：

1. 待审目录中的文件（本仓库当前字节）；
2. Git 把文件写入对象库后，暂存区／提交中的 blob 内容；
3. 从该提交全新检出的文件。

公开 Python 工具不执行 Git 操作。发布流程已建立本地提交并上传远程仓库，
随后通过全新远程克隆核对文件字节与哈希。整理阶段另在临时仓库中分别用
`core.autocrlf=false` 和 `true` 核对暂存区与全新检出文件；复核证据留在内部发布记录中。
后续修订沿用同样的检查方法，验收通过后再上传。

## 5. 与哈希清单的关系

`release_manifest.json` 与 `SHA256SUMS.txt` 记录的是第 1 段的字节。它们只有在第 2、3 段一致时
才有意义；因此换行属性属于发布阻断项，而不是风格问题。
